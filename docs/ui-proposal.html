home-management-system · interface proposal

One house,
one screen.

The engine is right. The ledger replays, the grammar is shared across three surfaces, and nothing writes without a plan you can read first. What is wrong is the chassis: five tabs, one per table, and every real task cut across all of them. This proposes throwing the chassis away.

Scope: internal/tui, internal/app Domain model: unchanged Command grammar: unchanged
01

What is actually wrong

Every complaint below has the same shape underneath it. The interface is organised around what the database stores — a tab per entity — and there is no task in this system that lives inside one entity. So every task becomes a tour of the tabs, and the thing you are working on is off-screen for most of it.

navigating between different categories and locations

Categories and Locations are two exclusive tabs that are the same widget showing two halves of one fact. A holding is an item-of-a-kind in a place; the interface will show you the kind or the place, never both, and switching drops your cursor. internal/tui/views.go — five viewSpecs, one per table

unlinked with the import

The import is a different application: a CLI subcommand, a folder on disk, and a plan screen that — in the code's own words — swaps the whole screen. verifying

The domain model specifies this flow in detail — walk a location, enter observed quantities, emit Counted and an explicit Adjusted for each discrepancy. It has no interface at all. hms verify is a command-line integrity check; the Integrity tab is prose; counting is #, one row at a time, in a flat table sorted by a column that is not where you are standing. This is the most physical task in the system — you are holding a shelf, not a keyboard — and it is the one with the least interface. docs/domain-model.md §4.5 — "Pick a Location, walk its Holdings, enter observed quantities"

02

Three moves

The replacement is not more screens. It is fewer: one screen, and everything transient arrives as a drawer beneath it rather than instead of it.

Move one

One tree, two lenses

Categories and Locations stop being tabs and become lenses on the same rail — one widget, one set of keys, one fold model. \ flips between BY PLACE and BY KIND and keeps what you are looking at: standing on an ancho chile in the garage, flip, and you are standing on Spices › Dried Peppers. The pane beside the rail always shows what is actually in there, rolled up over the subtree. The flat Holdings table stops existing; it was the contents pane with the root selected.

Move two

One review drawer

An import, a batch of structural edits, a reconciliation from a count — these are all a set of proposed commands shown against the present state. The code already has one mechanism for that (PlanAll → Describe → ApplyPlan) and three interfaces to it. Collapse them into a drawer that opens below the house, so walking the proposed rows walks the rail and the contents pane behind them. Each row shows its own before → after. Ready rows apply while blocked ones wait.

Move three

Verbs you can see

Thirty-five commands behind six keymap contexts is a vocabulary, not an interface. space opens the actions legal for the thing under the cursor, each annotated with the state it would change — and illegal ones are simply absent instead of being refused after you commit to them. The bar along the bottom stops being a fixed three-item reminder and becomes the four or five verbs that mean something right now.

04

The four tasks, resolved

Moving a thing

m opens the destination picker as a drawer, with what you are carrying pinned at the top of it and the rail still on screen behind. Type to filter by full path; the tree keys work unchanged, because it is the same tree. It takes a multi-selection, and it takes places too — moving a crate into a different bay is the identical gesture as moving the chile into the crate, because it is the identical idea. The typed reparent location command stops being the only way to do the common thing.

Adding and deleting categories

O puts the rail in organise mode, where structural edits are staged, not committed. Create a child with n and keep typing; d marks a node for deletion and says, in the row, where its contents will land; m re-parents. The drawer accumulates the diff and one a applies the lot as a single transaction. The domain model already says this reorganisation is free and migrates nothing — the interface should let you try a shape before you own it.

Importing, resolved against the present

Import starts inside the app (i) and the folder-and-handoff mechanism underneath is untouched — it is the privacy-correct design and it should not change. What changes is that the plan never takes the screen. Each row carries its own effect (2 bags → 2.1 kg), the cursor on a row points the rail and the contents pane at what it would touch, and ambiguity is settled in place with one key: did you mean Cumin? [y] [n] new. Stages still apply in passes; they now display as one list, because a file's consequences are one thing to understand. And a applies the ready rows and leaves the rest, rather than refusing the whole file because one row said "lots".

Verifying, and checking out

V on any node starts a walk of its subtree — the one deliberate full-screen mode in the design, because when you are counting a shelf you are not browsing a house. One holding at a time, set large, with the ledger's claim under it and three keys: it's right, it's this much instead, it's not here. Missing Unique holdings become Out with no location rather than being deleted, as §4.5 requires. The reconciliation lands in the same review drawer as everything else, showing Counted and Adjusted as the separate rows they are. Checkout stays what it already is: t, one keystroke, no questions.

06

What is not touched

This is a chassis swap. The parts that make the product trustworthy are the reason it is worth doing.

The command grammar

internal/command is the asset. One vocabulary serving the command line, a CSV header and a JSON Lines key set is what makes an agent-written import possible at all. Not one field changes.

Plan, describe, apply

Nothing writes without a readable preview. The new drawer is a better renderer for exactly this cycle, not a replacement for it — and the confirmations keep their honesty (permanent · changing these later replaces every holding).

Refusals that name the fix

only 100 g of "Ancho Chile" here, and 5000 g was asked for — it does not come in packages to open is a model error message. It keeps its wording and gains a better home: attached to the row it is about.

The widgets

tree, table, line, complete, editor are fine. They are assembled wrongly, not built wrongly.

The import folder and the handoff

Three directories with three authors, no default planner, and a workflow that degrades to "you write the plan file" is the right design and the right privacy posture. Only the entry and exit move into the app.

The nudge discipline

§1.4 is right and the current nudges obey it. The attention line at the top is one line, specific, and dismissible — it expands on a key and never nags in place.

How it lands

Seven phases, each shippable. The existing test harness carries the whole thing: the headless renderer and golden frames in internal/tui/testing mean every phase lands as a set of frames you can read in a diff, which is exactly how the current UI was built and is the reason replacing it is tractable at all.

Phase 1

The shell

Rail + contents + inspector + verb bar, replacing tabs 1–4. Lens flip with selection carried across. Contents rolled up over the subtree with a here-only toggle. No new domain work: this is CategoryTree, LocationTree, Holdings and Items recomposed.

Phase 2

The drawer

Generalise planview into a bottom drawer that never takes the screen, with per-row effect columns and cursor-follows-into-the-house. Port the import onto it and move its entry point inside the app. Add apply-the-ready-rows.

Phase 3

The act palette

Phase 4

Staged structural edits over the rail, accumulating into the drawer, applied as one batch. PlanAll already exists; what is new is holding a proposed tree shape in the UI and rendering it as a diff over the real one.

08

Where this could be wrong

Undo does not mean undo

The ledger is append-only and that is load-bearing. z can only ever mean "apply the inverse command", which works cleanly for Move, Consume, Receive, Rehome and the custody pair, and does not work for Retire, Gone, Demote or anything the model calls terminal. So undo must be offered per action and absent on the ones it cannot honour — an undo that silently no-ops on the scariest operation is worse than none. The toast should say z undo only when it is true.

Two panes need width

The current design degrades to 60 columns by dropping tab labels. A rail plus a contents pane cannot. Below roughly 76 columns the rail should collapse to a breadcrumb line with the contents pane taking the full width, and ← should re-open it as an overlay. That is a real fallback to design, not a resize rule.

space is currently select

Re-binding space from ToggleSelect to the act palette is the single change most likely to annoy on day one. C-@ still selects, and x joins it. If that trade is wrong, the palette can take . instead and nothing else in the design moves.

Staged structural edits create a second source of truth

Organise mode holds a proposed tree that the database has not seen. That is fine as long as it lives strictly in the UI and is rendered as a diff over freshly loaded rows — but it is the one place in this proposal where the architecture's "one owner per fact" rule could be quietly broken. Worth an archlint rule of its own: nothing outside tui/organise may hold an unapplied tree.

The walk assumes you brought the terminal to the shelf

It is designed for a laptop on the garage floor. If the real ergonomics are "phone in hand, laptop upstairs", the walk is the wrong shape and the right answer is that the walk produces a printable checklist and reads back a filled one — which is, notably, an import. Worth settling before phase 6 rather than during it.
